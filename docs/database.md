# База даних

PostgreSQL 17 + [Drizzle ORM](https://orm.drizzle.team/docs/overview) (драйвер
postgres.js). Локально база живе в Docker, на проді — у Neon. Один і той самий
код працює з обома — відрізняється лише `DATABASE_URL`.

## Швидкий старт локально

```bash
docker compose up -d      # Postgres 17 на localhost:5433
cp .env.example .env.local
npm run db:migrate        # застосувати міграції з drizzle/
npm run db:seed           # наповнити демо-даними (деструктивно!)
npm run db:studio         # веб-переглядач бази (Drizzle Studio)
```

Порт **5433** обрано навмисно, щоб не конфліктувати з іншим Postgres, який
може вже крутитися на 5432.

Повний скидання бази:

```bash
docker compose down -v && docker compose up -d
npm run db:migrate && npm run db:seed
```

## Схема

Єдине джерело правди — `src/db/schema.ts`. Типи таблиць (`Doctor`,
`Appointment`, ...) експортуються звідти — **імпортуйте їх, не дублюйте**.

```
users             акаунти (пацієнти й адміністратори)
specialties       довідник спеціальностей (тільки seed)
doctors           лікарі; "видалення" = is_active = false
doctor_schedules  тижневий розклад: лікар × день тижня → робоче вікно
appointments      записи на прийом зі статусом booked / cancelled
```

Зв'язки:

```
specialties 1 ─── n doctors 1 ─┬─ n doctor_schedules
                               └─ n appointments n ─── 1 users (пацієнт)
```

### `doctor_schedules` — розклад, а не готові слоти

Ми **не** зберігаємо кожен слот окремим рядком. Зберігається тижневий розклад:
для лікаря і дня тижня — робоче вікно та тривалість слота:

| Колонка | Приклад | Пояснення |
| --- | --- | --- |
| `weekday` | `1` | день тижня як у JS `Date.getDay()`: 0 = неділя, 1 = понеділок … 6 = субота |
| `start_time` / `end_time` | `09:00` / `17:00` | робоче вікно в часі клініки (Europe/Kyiv) |
| `slot_minutes` | `30` | тривалість слота: 15, 30 або 60 (CHECK у базі) |

На лікаря і день тижня — максимум один запис (унікальний індекс
`doctor_id + weekday`).

**Вільні слоти обчислюються на льоту** чистою функцією
`computeFreeSlots(schedule, bookedStartTimes, from, days)` з
`src/lib/availability.ts`: розгортаємо розклад на найближчі 14 днів і
віднімаємо заброньовані записи та минулий час. Ніяких «згенерованих слотів» у
базі, які закінчуються або розсинхронізовуються з розкладом.

### `appointments` і захист від подвійного бронювання

Запис зберігає `doctor_id`, `patient_id`, `starts_at`, `ends_at`, `status`
(`booked` | `cancelled`), `created_at`, `cancelled_at`.

Головний механізм цілісності — **частковий унікальний індекс**:

```sql
CREATE UNIQUE INDEX appointments_doctor_starts_at_booked_unique
  ON appointments (doctor_id, starts_at)
  WHERE status = 'booked';
```

Що це дає:

- у лікаря не може бути двох **активних** записів на той самий час;
- скасований запис (`status = 'cancelled'`) не блокує час — його можна
  забронювати знову, а історія зберігається;
- захист працює **в базі**, а не в коді. Перевірка "чи вільний слот" перед
  INSERT-ом не рятує від гонитви: два запити можуть одночасно побачити слот
  вільним і обидва спробувати вставити. Перший INSERT пройде, другий впаде з
  помилкою Postgres `23505` (unique violation).

Готова функція `bookAppointment` (`src/db/queries/appointments.ts`) ловить
`23505` і кидає типізовану `SlotTakenError` — UI має показати дружнє
повідомлення й оновити список слотів.

**Як відтворити гонитву руками:** відкрийте профіль лікаря у двох вкладках,
в обох натисніть той самий слот і підтвердіть. Перша вкладка отримає
підтвердження, друга — повідомлення, що час уже зайнятий.

## Правила роботи з міграціями

1. Схема змінюється **тільки** у `src/db/schema.ts`.
2. Після зміни: `npm run db:generate` — drizzle-kit згенерує SQL-файл у
   `drizzle/`. Подивіться цей SQL очима і закомітьте його **разом** зі зміною
   `schema.ts`.
3. **Ніколи не редагуйте вже застосований файл міграції.** Потрібно щось
   змінити — робіть нову міграцію.
4. Після `git pull`, якщо з'явилися нові файли в `drizzle/` — запустіть
   `npm run db:migrate`.
5. Прод-міграції запускає тільки супервайзер (див. docs/deployment.md).

## Тести і база

Unit-тести **не ходять у базу**. Тестуємо чисті функції з
`src/lib/availability.ts` (приклад — `src/lib/availability.test.ts`).
Уся логіка, яку хочеться тестувати, має жити в чистих функціях; функції з
`src/db/queries` перевіряємо руками через застосунок.
